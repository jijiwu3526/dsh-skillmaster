# DSH Web 协议与 Preset 版本说明

## 两代会话 RPC

| 操作 | 较新 Remote Web | 较旧 API Proxy Web |
| --- | --- | --- |
| 预设列表 | `POST /api/agentPresets/list`，`payload: {args:{}}` | `POST /api/agentPreset.list`，`payload:{}` |
| 创建会话 | `POST /api/session/create`，`payload:{args:{request:{...}}}` | `POST /api/session.create`，`payload:{...}` |
| 登记工作区 | `POST /api/workspace/create`，`payload:{args:{request:{path}}}` | `POST /api/workspace.create`，`payload:{path}` |
| 发送消息 | `POST /api/session/prompt`，`payload:{args:{request:{...}}}` | `POST /api/session.prompt` |
| 会话列表 | `POST /api/session/list` | `POST /api/session.list` |
| 会话导出 | `GET /api/session.export?sessionId=...&includeDescendants=true` | 同一路径（需目标版本提供导出功能） |

两代上行信封均为 `{type:"client-request",rpcId,method,payload}`，下行校验 `server-response` 与相同 `rpcId`。较新 Web 的启动链接包含一次性 token，访问后发放签名 Cookie；之后的 `/api` 请求须携带 Cookie。较旧 Web 可能不需要该交换。脚本只针对路由缺失（404）尝试旧协议。

Web Remote 的参数字段由服务端 TypeScript 方法签名生成，因此升级 DSH 后若出现 `arguments-invalid`，应先检查目标版本 `session/create`、`workspace/create` 的实际签名。脚本不会试探性地用不同权限参数反复创建会话。

## 已在 0.1.5-rc.1 上核对的实际形状

以下取自本机安装的 DSH 生成的 Typert 描述符，非推测：

| 事实 | 依据 |
| --- | --- |
| `session/create` 的 `args.request` 字段名确为 `request` | `dsh-api-session-controller/lib/typert.host.js` |
| `SessionCreateRequest = {workspaceId?, cwd?, sessionId?, agentPreset?}` | `lib/types/types.d.ts` |
| 错误分支是扁平的 `{code, message, details}`，**不是**嵌套 `failure` | `dsh-client-connection/lib/types/rpc.d.ts` |
| 无主端点返回 HTTP 404；已知端点的业务失败是 HTTP 200 + `ok:false` | `createSharedFetchHandler` 与 `ConnectionRpcResult` |
| 导出端点只接受 `GET` / `HEAD` | `dsh-session-log-export` 的 `fetch.register` |
| `session.export` 缺 `sessionId` 或 `includeDescendants` 非 `true/false` 时返回 400 | 同上 |

> 关于 `failure`：脚本的容错写法 `error.get("failure", error)` 对两种形状都成立，
> 扁平分支正好命中 `error` 本身。**这不是 bug，而是对两代协议的兼容写法。**

## `blank` 机制：为什么新建会话在侧栏看不见

`SessionSummary` 带有 `blank` 字段，语义是「折叠后的事件前缀中没有任何轮次」。
**Web 侧栏会隐藏 `blank: true` 的会话。**

因此 `session/create` 成功 ≠ 你能在 Web 里看到它。实测确认：
`session/create` 返回成功、`session/list` 中能查到、`session.export` 也能导出，
但侧栏没有入口，直到发出一条消息。

`send` 子命令发一条即可解决。`session/prompt` 请求形状：

```json
{"args":{"request":{
  "requestId":"<uuid>",
  "sessionId":"<sid>",
  "mode":"queue",
  "content":[{"type":"text","text":"..."}]
}}}
```

`mode` 取 `queue`（入队）或 `steer`（插队）。成功返回 `{"accepted": true}`。
注意「已接受」只表示进入 Agent 收件箱，不表示模型已回复。

## 预设 API 只有读，没有写

`agentPresets` 命名空间在 0.1.5-rc.1 上只有五个方法：

| 方法 | 用途 |
| --- | --- |
| `list` | 预设名册，含 `trust` / `isDefault` / `broken` |
| `read` | 读取单个预设的完整 YAML |
| `copy` | 从已有预设复制出新预设 |
| `deletePreset` | 删除预设 |
| `select` | **给某个会话**换预设，不是设置默认 |

**没有写入方法。** 定制预设只能落盘到 `~/.dsh/.agent-presets/<id>/agent.cordis.yml`，
由 DSH 在挂载时读取。设默认预设同样没有 API，只能在设置页点击。

`agentPresets/read` 与 `copy` 的参数是**裸具名字段**（`args.agentPreset`、`args.from`、
`args.id`），不走 `args.request` 包装——与 `session/create` 不同，容易写错。

### roster 的 `broken` 字段是排障第一现场

`list` 返回的每个预设带 `broken?: string`，内容是**具体原因**，例如：

```
"the composition must be a top-level list of plugin rows"
```

挂载失败分两类，错误质量差别很大：

| 类型 | 表现 | 排障方式 |
| --- | --- | --- |
| 预检可发现 | `broken` 被填，脚本在 `session/create` **之前**就拦下 | 读 roster 的 `broken` 拿一手原因 |
| 预检发现不了 | `session/create` 时才报挂载错误 | 错误含**文件路径 + 字段 + 原因** |

例：删除 persona 的 `prefix` 属于第二类，DSH 报
`failed to apply loader entry persona: $.prefix missing required value`，
直接指出 `~/.dsh/.agent-presets/<id>/agent.cordis.yml`。
`@deepseek-ai/dsh-persona` 的 `prefix` 与 `complete` 在某些配置下是必填的，
即使自定义内容都写在 `suffix` 里也不能省。

## 工具面的权威来源

会话导出 ZIP 的 `request/header` 事件里，`data.header.tools` 是 **DSH 实际发给模型的
工具清单**。它比「问模型你有哪些工具」可靠得多——后者会因格式漂移而失真
（实测同一预设得到 13 / 2 / 0 三种结果）。

用这个字段可以程序化断言「某预设裁掉了某个工具」，无需解析自然语言。

该清单**不含**宿主 profile 注入的插件（如 `mcp__computer_use__*`、`mcp__node_repl__js`），
这正好界定了预设的能力边界：**预设裁剪 DSH 自带工具链，管不到宿主注入的插件。**
要真正限制工具面必须在宿主配置层处理。

## Preset 配置格式

| DSH 代际 | 预设载体 | 配置工作方式 |
| --- | --- | --- |
| 早期 0.1.x | `$DSH_HOME/.agent-presets/<id>/agent.cordis.yml` | 目录发现，设置中的预设默认值 |
| 0.1.7 系列及当前上游 | profile/bundle patch 里的 `@deepseek-ai/dsh-agent-preset` 声明 | Creator/设置编辑 profile 的声明和默认值 |

两种载体的插件子行与 persona 字段会随版本变化。本项目刻意不提供一个假定所有 DSH 版本可直接复制的固定 `agent.cordis.yml`：实际配置由 Creator 在目标安装环境中读取基线并生成。保留 Creator 最终生成的配置副本是安装后的必要归档步骤。

## Python SDK 的取舍

官方 Python SDK 的 `sdk-minimal` 运行时是独立应用，按 SDK 的会话 ID 创建会话；官方文档说明 Web 是单独的 CLI 应用。该 SDK 的创建路径没有加入 Web 会话的 Agent Preset roster，因此这里用 Web 本身的会话 RPC，以避免“创建成功却没挂上预设”的情况。
